## 01 项目方向与已确认决策

### 1.1 最终体验

用户在手机记账，离线也能完成本地保存；需要在电脑继续使用时，用临时9位PIN绑定新设备，再手动上传或下载完整台账。每次覆盖之前看清来源、版本和差异。云端暂时不可用，既有本地台账仍可查看、记账和导出。

性能优化应让启动、切股、查找、记成交和大文件导入更流畅；易用性优化应让用户知道“哪份账、这笔是什么、保存到哪里、哪里还要处理”。界面不能为了简洁隐去真实欠股、成本来源或冲突，也不能把参考价展示成实际成交。

### 1.2 用户已确认的产品选择

| 事项 | 已确认内容 | 后续执行约束 |
| --- | --- | --- |
| PIN用途 | 首次创建账本，其他设备通过临时9位PIN加入 | PIN不作为永久登录密码，不作为公开账本主键 |
| 首版同步 | 手动上传、手动下载，核对后恢复 | 不自动合并不同设备的离线修改，不静默覆盖 |
| 云端偏好 | 托管数据库，优先免费，不维护独立后端服务 | 推荐Supabase，仍须配置SQL、认证、权限和受控数据库函数 |
| 现有部署 | GitHub Pages继续承载前端 | 不为了同步强制换框架、换托管或取消PWA |
| 迭代方式 | AI可以多轮优化，重视完整性与维护质量 | 一轮完成一个可验收结果，实测、更新文档、交接下一步 |

**推荐但尚未完成验证的决定**：采用Supabase匿名认证作为设备会话入口、PostgreSQL行级权限作为账本隔离、完整快照作为首版同步单位。选择云区、恢复方案、PIN防滥用策略及发布开关，需要在对应任务中验证，不能从“推荐”直接改成“已上线”。

### 1.3 优先级与成功标准

1. **账务与隔离正确**：每笔事实只记一次，跨账本不可读写，来源关系完整。
2. **可恢复**：错误上传、冲突、掉线、浏览器退出和更新失败后有明确恢复路径。
3. **离线可用**：本地保存不等待网络；同步失败不回滚已保存成交。
4. **操作清楚**：上传、下载、切账本、撤销的影响可见，错误可定位并处理。
5. **性能有证据**：在固定设备、数据和构建下测量改善，不以主观“更快”结案。
6. **维护成本可控**：使用少量清楚的模块，避免为未来假设引入复杂框架。

第一版不追求多人实时协作、自动交易、云端重算盈利、逐字段冲突合并、无限历史或端到端加密。这里的延期不否定价值，而是避免把这些能力混进首版的安全边界。

### 2.2 必须保持的业务不变量

- 金额和价格以整数分处理；非法输入拒绝或明确缺失，不出现NaN、Infinity或溢出。
- 用户记录、实际回补成交、成交流水凭据与来源分配分别保存；合成高位卖出和虚拟库存不是新增事实。
- 盈亏、库存、欠股、奖励、回本链和建议仍由domain统一派生，不能在云端或页面复制另一套公式。
- 欠股回补与可选再买、低位回本与底仓做T保持身份隔离；同价也不能误并。
- 先卖后买默认低位回本，自动关联同股、卖出时已买入的高位未占用批次；显式底仓做T、人工关联与解除覆盖优先。
- 收益日历、年/月累计、月度列表和趋势是独立表现视图：普通先买后卖只计实际正盈利，先卖后买整单基础股全部实际买回后按最后所需回补日期确认实际价差；部分回补不确认、奖励不抵基础股、计划价不算收益。该视图不能回填真实总账、回本链或奖励池；统计页账务汇总仍展示真实总账。
- 做T回补保留实际成本，仅恢复已配对份额的原高位目标；多买部分独立保留。
- 回补节省、做T策略价差不能重复加进全局已实现盈利；未知日期不能猜成已回补。
- 推荐过滤不改变原欠股。缺昨收或日内区间，不能用云端快照假装今日已确认行情。
- 软删除仍保留历史引用，依赖保护与备份恢复语义不能因分页、裁剪、同步而失效。
- 所有编辑弹层保持背景滚动位置，按钮强调与页面动效遵守现有统一实现。
- 不用清空IndexedDB、整站缓存或用户数据修复应用更新、图标、登录或云同步问题。

### 2.3 已知问题先复核，不能携带旧结论上线

[操作边界与核对](操作边界与核对.md)按稳定编号保留最新状态。2026-11-05已修C01–C04的明确反例及D08–D10，D06/D07当前契约加强；O03已在前轮修复，O06、D11及V05未覆盖的底层组合等继续保留。收益日历与批次指标仍须分别核对，不能只看旧状态或固定测试数下结论。

每项要补“当前复现输入、期望、实际、代码版本、修复或未复现证据”。尤其关注：亏损归属脱链、第二代回补、同日结束、计划成本冒充实际成本、奖励实际金额、非法日期/小数股数/1904日期系统、恢复引用与极端数值。高风险输入若尚不被严格校验，先补校验和复现，再允许云快照写入本地。

## 03 云端方案与成本边界

### 3.1 推荐Supabase的理由与实际限制

Supabase提供托管PostgreSQL、认证、行级权限和前端可调用的数据API，适合保留当前静态前端。2026-11-03核验的免费套餐包括500MB数据库、5GB出站流量和最多两个活跃项目；免费项目闲置一周后可能暂停。[官方价格](https://supabase.com/pricing)

这些是当前套餐信息，不是永久免费承诺。未登录、超额、被暂停、网络不可达都需要在产品里有可理解的状态。没有必要为了规避暂停而添加无业务意义的保活请求。

“不写后端”在本方案中指**不维护独立Node服务和自建服务器**。权限、PIN兑换、版本比较和原子提交仍需要数据库约束、RLS与受控SQL函数。[数据库函数说明](https://supabase.com/docs/guides/database/functions)

### 3.2 正式使用前的选型验证

- 用实际电脑、安卓浏览器、iPhone Safari/PWA分别验证认证、读写、休眠后恢复、断网和过期会话。
- 选择云区前在用户常用Wi-Fi和移动网络实测；记录连接成功率与延迟，不承诺某境外云区在国内始终可达。
- 如果网络体验不满足要求，再对腾讯CloudBase等国内托管方案做同一组对照；重新核验长期免费条件，不根据旧宣传承诺永久免费。
- 用虚构台账做PoC，不把真实交易或用户文件放进公共演示库、仓库fixture或第三方测速服务。
- 单独测试环境与生产环境；公开前端配置只允许项目URL与publishable key。`service_role`、secret key、数据库密码不能进入Vite变量、浏览器、日志和Git。

Supabase区分可公开的publishable key与可绕过RLS的服务端密钥。API key标识应用，Auth会话标识调用者；知道公开key不应获得其他账本权限。[官方密钥说明](https://supabase.com/docs/guides/getting-started/api-keys)

### 3.3 费用估算与保留策略

采用可见参数：活跃账本数A、平均快照字节S、每账本保留版本数R、每天上传U次、下载D次。

```text
快照原始占用 ≈ A × S × R
每月下载数据量 ≈ A × S × D × 30
```

另计数据库索引、认证表、元数据、TOAST、审计、失败重试与协议开销。不要把原始JSON占用直接等同于账单，也不要把所有原始历史在每次版本中无限重复保留。

建议首版默认保留最近10个云端版本，设置每账本总量上限与全项目告警阈值；这两个数是待测容量策略，不是免费套餐保证。先测实际S，再定最大快照、每日操作量和清理方案。清理只能删除不再被head指向、超过保留策略的版本，不能删唯一恢复来源。下载本地JSON仍是独立备份通道。

## 04 身份、设备绑定与恢复设计

### 4.1 身份模型

| 名称 | 意义 | 不能混用的对象 |
| --- | --- | --- |
| `ledgerId` | 随机账本UUID，稳定标识一份账本 | 不是PIN，不是授权凭证 |
| `principalId` | Supabase Auth身份，取服务器会话中的`auth.uid()` | 不能相信客户端传入的userId |
| `installationId` | 本地安装标识，帮助诊断与展示 | 不是安全身份，不能单独授予权限 |
| 设备成员 | principal与ledger之间的有效成员关系 | 设备名称、浏览器指纹不是认证证明 |
| PIN | 一次性、短期的加入请求入口 | 不是永久账号或加密密钥 |
| 恢复码 | 高熵的一次性或可轮换恢复秘密 | 不能使用同一个9位PIN代替 |

匿名认证可以做到无需邮箱，但清浏览数据、退出身份或换设备后不能自动访问原匿名账号，因此必须另外设计账本成员绑定和恢复。[匿名认证说明](https://supabase.com/docs/guides/auth/auth-anonymous)

首版建议一个已认证身份对应一个安装的权限主体；复制浏览器会话不等于新增独立设备。设备列表应说明“已授权会话/安装”，不把它宣传成硬件级身份认证。后续可绑定邮箱或Passkey改善恢复，但须另写迁移设计。

### 4.2 创建云端账本

1. 本地已有账本仍照常使用，未开同步时不创建云端账号、不自动发出个人数据请求。
2. 用户明确点击“开启云端同步”，完成匿名认证与环境可达性检查。
3. 数据库事务创建账本和owner成员，记录服务器时间。初始head为空，不假装已经上传。
4. 展示恢复方案，用户保存恢复材料后才能把唯一数据长期依赖云端。
5. 第一次上传前预览当前本地账本的股票、记录数、实际成交和异常；云端非空则进入冲突或加入流程。

### 4.3 临时9位PIN与原设备确认

建议PIN按字符串处理，允许前导0，显示为三组三位；用安全随机源生成，活跃PIN有唯一约束。默认10分钟有效是初始产品建议，期限由服务器时间判定。

```text
原设备生成邀请 → 新设备输入PIN并发起加入请求
→ 原设备看到设备名与核对短语 → 明确同意
→ 数据库原子消费邀请并创建新成员 → 新设备获得成员访问权
```

- 新设备在确认前不能读取账本名、交易摘要、恢复码或快照。
- 成功申请不是授权成功；原设备未同意时，新设备保持等待并允许取消。
- 原设备确认具体的申请身份，并核对双方短语；不能自动批准“第一个知道PIN的人”。
- 一个邀请只批准一个申请；到期、撤回、重复确认、并发申请都在数据库事务中检查。
- PIN可重发，重发即撤销旧邀请；不可通过列出邀请表获取所有活跃PIN。
- 不在URL、分享链接、埋点、异常日志或审计正文记录明文PIN。存储短码的普通哈希仍可穷举，应使用受控验证、服务端秘密保护的摘要及严格限次。
- 统一失败文案避免提供有效PIN探测接口；失败次数和等待时间由服务端判定，刷新页面不能重置。

9位数字只有约30比特搜索空间。原设备确认降低盗取风险，但不解决批量请求、骚扰或资源耗尽；前端按钮冷却不是防护。

**必须在PoC解决的防滥用边界**：匿名注册的CAPTCHA/限流与PIN兑换限流是两件事。数据库按principal限次可被批量新身份绕过。纯SQL方案至少要有邀请/账本/全局事务预算、请求上限和过期清理，并实测攻击面；若还需要可信IP限流或校验外部验证码，可能需要托管Auth Hook、网关或少量Edge Function。不能把客户端自报IP当真，也不能声称“仅前端＋RLS已经解决所有猜码”。如果纯SQL达不到要求，应暂停开放兑换入口，说明最小托管校验组件的必要性，而不是降低权限。

Supabase官方建议匿名登录启用CAPTCHA以降低滥用，但它不自动保护自定义PIN接口。[防滥用说明](https://supabase.com/docs/guides/auth/auth-anonymous#preventing-abuse)

### 4.4 设备管理与权限

首版至少区分owner和member。owner管理邀请、设备撤销和恢复材料；member读取、上传、下载。数据库禁止member自行升权、批准自己、修改owner或撤销最后一个有效恢复管理者。

每次读取、提交和批准均检查当前有效成员。不要只把权限写进可能长时间有效的JWT后不查成员表；撤销之后旧token的后续云端请求也必须被拒绝。已撤销设备本地已下载的明文无法远程收回，设备管理文案要如实说明。

### 4.5 恢复与退出

建议提供至少128比特随机恢复码，云端只保留验证摘要，恢复成功绑定新身份、轮换恢复码、记录恢复事件；不把PIN、用户备注或邮箱当恢复秘密。

- 恢复入口也需限流、原子使用和敏感日志脱敏。
- 明确“恢复并加入”与“恢复并撤销全部旧设备”两种影响，不能默认为所有设备退出。
- 用户不保存恢复材料且所有身份都丢失时，不能承诺后台可无条件找回。
- 退出云同步保留本地账本。退出、解绑、删除本地副本、删除云端账本是不同操作，分开说明。
- 删除云端账本后，离线旧设备不能重新上传并复活原账本；重新启用应创建新ledgerId并由用户确认。
- 恢复码或设备令牌不是JSON台账业务字段，不跟随普通Excel或云快照导出。

### 4.6 数据保护边界

首版按TLS、云平台存储保护及严格授权实现；这不等于端到端加密，项目管理员的权限仍需管理。若以后做端到端加密，应设计高熵账本密钥、安全跨设备传递、轮换与恢复，不能用9位PIN直接派生可离线穷举的唯一密钥。强度未知时，不在界面使用“任何人都无法读取”等承诺。

## 05 同步数据契约与本地隔离

### 5.1 完整快照包含什么

以现有完整备份的原始输入为基础，逐张声明包含与排除，不能临时漏表。

| 数据 | 首版是否同步 | 说明 |
| --- | --- | --- |
| records及软删除历史 | 是 | 保留sourceRow、原Excel行、importKey、来源及录入顺序 |
| stocks、计算设置 | 是 | 股票间隔、启用和影响账务的配置 |
| rebuyExecutions、bookingReceipts | 是 | 实际成交、奖励及来源分配、撤销状态不可丢失 |
| extraTargets、buyTargets、plans | 是 | 包括strategy与已用历史档，不只上传当前可见档 |
| hedges、chainLinks、merges | 是 | 空人工覆盖、结束时间、成员顺序和来源保留 |
| batches、auditLogs | 是 | 首版完整保留；大体积归档须另立兼容协议 |
| lots/sells/orders/targets/chains/totals | 否 | 下载后用同版本domain重算，不当成输入写库 |
| PIN、token、恢复秘密、设备认证 | 否 | 单独身份与成员系统，绝不进入普通快照 |
| 昨收确认、日内区间、页面筛选 | 默认否 | 设备会话；跨天和跨股不自动继承确认 |
| 沙盒、未保存表单、滚动位置 | 否 | 本地临时状态，不能混入真实台账 |
| 公共估值快照、字体、应用资源 | 否 | 随应用发布，不作为个人数据重复上传 |

同步账本不等于同步浏览器全部localStorage或Dexie meta。先建立明确字段白名单，不能“为了省事”整库抓取包含凭证的元信息。

### 5.2 三种版本与快照封装

必须区分：备份结构`schemaVersion`、同步协议`protocolVersion`、领域计算口径`accountingVersion`。`appBuildId`只作诊断追溯，不能按字典序或时间替代结构兼容判断。

建议封装如下，字段名为规划契约，代码实施前需定稿：

```json
{
  "protocolVersion": 1,
  "ledgerId": "uuid",
  "snapshotId": "uuid",
  "baseRevision": 5,
  "commandId": "uuid",
  "schemaVersion": 14,
  "accountingVersion": "明确的口径标识",
  "appBuildId": "构建号",
  "payloadHash": "sha256",
  "contentHash": "sha256",
  "payloadBytes": 12345,
  "payload": { "records": [], "其余必须表": [] }
}
```

`revision`与`createdAt`由服务器分配，不信任客户端的时钟；`baseRevision`是上次共同版本。云端还保存提交principal、服务器提交时间和显示用设备名。ID不以本地时间戳单独保证唯一。

### 5.3 稳定序列化与摘要

- `payloadHash`针对确定编码的传输内容，校验损坏和重复提交。摘要不是签名，也不证明提交者拥有权限。
- `contentHash`针对声明过的业务内容，排除导出时间、最后检查时间等易变包装，避免“只导出一次就变脏”。审计和真实业务变化仍要计入。
- 对象键顺序可稳定化，数组顺序必须逐表定义。不能对所有数组无差别排序：录入顺序、FIFO奖励、来源分配和同时间事件可能依赖顺序。
- 恢复后与原快照逐字段、身份和领域结果核对，不仅比较总金额。金额一致不代表来源和链一致。
- 压缩在体积实测后选择；限制压缩前后大小、解压比和解析深度，防止大包拖垮浏览器。
- 首版不要依赖上传方给出的股数、盈利、错误计数作为校验依据。摘要与预览在下载端重算。

### 5.4 无副作用快照与同步元数据

`readLedgerSnapshot`已在单个只读事务中抓取全部业务表与计算设置，不更新备份时间。M02仍需在同一读取中加入尚未实现的`localRevision`。网络调用发生在事务外，避免Dexie事务因等待网络中断。

单独保存同步元数据：ledgerId、当前副本ID、localRevision、baseRemoteRevision、baseContentHash、最近成功上传/下载、未完成commandId及其摘要。不改变现有账务主键，不把“最近检查”当成“最近成功”。

每次影响同步内容的写操作在同一业务事务内增加localRevision。覆盖新增、编辑、撤销、删除、回滚导入、计划、拆档、股票配置、结束链和恢复；不能只监听React状态或依赖目前未必完整的审计推断dirty。估值刷新、搜索和弹层不增加业务修订。

### 5.5 本机隔离与旧库迁移

建议通过数据库工厂实现每账本独立命名空间：例如`grid-trading:<localReplicaId>`。云ledgerId与本地副本映射单独登记；数据库名不是安全边界，目的是防误串账和原子切换。系统仍需RLS保护云端。

旧`grid-trading`库只在迁移流程中读取。先备份，复制到隔离副本，校验结构、关系、股数与来源，确认成功再切active指针；不先删旧库。迁移中断可重试，不能每次启动复制成新账本。

- 切账本先关闭或处理草稿，解除旧订阅，重建provider状态、清理沙盒和会话确认；旧请求返回时不得写到新账本。
- 请求捕获ledgerId、replicaId、generation。异步结果回写前检查仍是同一上下文。
- 多标签通过锁与广播协调迁移、恢复和切换，必要时提示旧标签重新进入。单独BroadcastChannel消息不是数据库锁。
- 切换失败保持原账本可用；不在内存短暂显示上一用户记录。
- 本地不依赖云登录才能打开自己的已保存账本；共享设备还需用户明确区分“退出授权”和“删除本地副本”。

## 06 上传、下载、冲突与故障恢复

### 6.1 同步状态机

| 状态 | 含义 | 可用动作 |
| --- | --- | --- |
| 未启用 | 只有本地台账 | 开启、导出本地备份 |
| 未绑定 | 有会话但无账本成员资格 | 创建或申请加入 |
| 待确认 | PIN申请已提交，原设备未批准 | 等待、取消、重试邀请 |
| 一致 | 本地内容与已确认共同版本一致 | 检查云端、查看历史 |
| 本地有修改 | 本地领先于共同版本 | 上传；下载前保留本地分支 |
| 云端有新版 | 本地无业务修改，远端已更新 | 下载预览后恢复 |
| 双端有修改 | 本地、远端都离开共同版本 | 冲突核对，不自动覆盖 |
| 正在传输 | 请求在途，结果未确定 | 本地可继续记账，限制同一同步操作重复提交 |
| 结果待确认 | 云提交可能成功但客户端未收到 | 按commandId查询原结果，不能盲目新建提交 |
| 离线或服务不可用 | 网络失败、云暂停、配额不足 | 本地记账、备份、手动重试 |
| 授权失效 | 认证过期或成员被撤销 | 重新认证/绑定；本地数据保留 |
| 不兼容 | 协议/结构/口径不受支持 | 更新应用或保留文件，不部分恢复 |

“检查失败”不能显示“一致”；“上传成功”不能暗示上传期间的新成交也已上传。状态不能只用颜色区分。

### 6.2 上传事务

1. 从当前副本捕获ledgerId、localRevision、baseRemoteRevision及完整快照。
2. 本地校验结构、必填表、唯一性、外键、策略引用和可接受体积；计算摘要及预览。
3. 用户确认后提交固定commandId。相同ID必须对应相同账本、基线和内容。
4. 云事务锁定账本head，检查有效成员和账本未删除，再比较headRevision与baseRevision。
5. 同事务写入不可变快照、更新head revision、写幂等结果；失败不留下半个版本。
6. 客户端按服务器结果更新共同版本。若localRevision已变化，仍保留“本地有修改”。
7. 断线重试先查同commandId结果；同ID不同内容返回错误，不覆盖原提交。

权限检查和head更新要具有一致的并发语义。撤销成员与提交并发时必须定义事务顺序并验证；不能在事务外先查权限，隔一会儿再直接写head。直接插表、update、REST和RPC都不能绕过同一规则。

### 6.3 下载与本地落地

1. 读取固定的snapshotId、revision、大小、协议与结构，不只拿“最新”字符串。
2. 下载完整包，校验摘要、结构、ID、引用和计算口径；在临时副本重建ledger。
3. 显示两侧关键差异：记录、买卖股数、净持仓、欠股、实际盈亏、回补/策略/链/回执数量及详细来源变化。
4. 用户确认前创建可恢复的本地检查点；必要时同时提供JSON下载。浏览器自动下载不能作为唯一成功凭据。
5. 确认时重新核对localRevision与当前ledger上下文，若预览后又记了成交，拒绝按旧预览覆盖。
6. 原子切换验证完的本地副本与同步元数据，或者在单事务完成替换；不可逐表清空再逐表网络拉取。
7. 新数据成功打开并复核后显示完成；失败恢复旧active指针并保留故障证据。

若预览期间云端又有新版本，可以恢复刚才已明确核对的不可变revision，但必须标示“云端已有更新，当前未到最新”。不能把旧revision显示成最新版。下载后的本地记录不因为下载动作本身伪装成全部新增成交。

### 6.4 首版冲突规则

共同版本为5，手机新增成交并上传为6；电脑基于5也有修改，则电脑上传必须返回版本冲突。

用户可选择：保留电脑副本稍后核对；先备份电脑后恢复云端6；将电脑副本另存为独立本地账本。任何“以本地替换云端”都须重新读取当前head、展示影响、保留远端旧版本，并按最新base做一次显式新提交，不能提供绕过CAS的force写入接口。

不按updatedAt自动选择、不按sourceRow合并、不按importKey去重后直接拼接、不按总金额相同判定无冲突。撤销和软删除也属于业务修改。未来自动合并必须另行解决跨设备稳定身份、来源重映射和事务级业务语义。

### 6.5 故障矩阵

| 故障 | 应有行为 | 验证方式 |
| --- | --- | --- |
| 上传前离线 | 不产生云版本，本地保持dirty | 断网提交 |
| 云提交成功后响应丢失 | 查询原command得到原revision | 代理丢响应后重试 |
| 上传期间新增成交 | 只确认捕获的旧内容，新成交仍待上传 | 延迟请求并记成交 |
| 同时两台上传 | 同base仅一台成功，另一台冲突 | 双会话并发 |
| 下载包损坏或超大 | 不修改原库 | 篡改/大包fixture |
| 下载预览后本地又修改 | 旧预览不能覆盖 | 预览期间另标签记账 |
| 下载落地时浏览器崩溃 | 旧库或完整新库可打开，不半包 | 分阶段中断迁移 |
| 被撤销设备持旧token | 新云读写拒绝，本地已下载数据保留 | 复用真实旧会话 |
| 云端暂停/配额满 | 本地可用，显示具体失败与重试入口 | 模拟对应响应 |
| 旧前端遇新快照 | 明确不兼容，不删未知字段后硬读 | A/B包及新schema |
| 删除云账本后旧设备上线 | 不自动重建已删账本 | 删除后重试旧提交 |
| 切账本时旧请求返回 | 不写入当前另一账本 | 延迟响应＋切换 |

## 07 建议模块与云端表职责

### 7.1 本地模块边界

以下路径是建议创建位置，**当前并不存在即不代表已实现**；实施时先查仓库，避免重复造同名模块。

```text
src/domain/sync/       协议、内容规范化、冲突判定、差异与纯校验
src/io/cloud/         Supabase适配、网络错误归一化、协议序列化
src/store/sync/       会话、设备绑定、修订、捕获与恢复编排
src/store/ledgerDb.ts 数据库工厂、隔离副本、迁移和active指针
src/pages/manage/     云同步、绑定设备、冲突预览与恢复入口
supabase/migrations/ 表结构、约束、RLS、RPC与权限迁移
supabase/tests/       真实数据库权限、并发与幂等测试
```

`useApp`继续提供唯一公开业务写入口，可以委托事务服务；拆文件不意味着页面获得直接写db权限。domain不导入Supabase或React；网络适配不计算盈亏；展示不持久化派生库存。

### 7.2 云端最小表模型

| 表 | 关键字段/约束 | 访问原则 |
| --- | --- | --- |
| ledgers | UUID、owner、headRevision、headSnapshotId、deletedAt | 仅有效成员读；head经受控提交变更 |
| ledger_members | ledgerId、principalId、role、revokedAt、授权时间 | 成员不自行增权；不能枚举其它账本成员 |
| snapshots | ledgerId、snapshotId、revision、协议、摘要、payload、作者、服务器时间 | 不可变、按账本授权、有体积限制 |
| sync_commands | ledgerId、principalId、commandId、请求摘要、结果revision | 幂等结果与快照同事务，重用ID不同内容拒绝 |
| pairing_invites | 受保护的PIN摘要、到期、状态、创建者、限次信息 | 无客户端全表读取，明文不落公开列 |
| pairing_requests | 邀请、申请principal、短语、到期、批准状态 | 申请者仅看自己的等待状态，owner确认指定请求 |
| recovery_secrets | 账本、恢复验证摘要、代次、失效状态 | 不可直接读取，受控恢复流程使用 |

可合并部分职责减少表数，但不能因此丢掉原子性、授权或审计。RLS不能只写SELECT策略：INSERT的WITH CHECK、UPDATE新旧行、DELETE、函数权限、view和Storage（若使用）一起核对。[RLS官方说明](https://supabase.com/docs/guides/database/postgres/row-level-security)

### 7.3 建议RPC契约

| RPC职责 | 输入重点 | 服务器必须保证 |
| --- | --- | --- |
| 创建账本 | commandId、显示名 | auth身份取自会话，创建和owner授权原子 |
| 创建邀请 | ledgerId | 当前owner、随机唯一PIN、过期和预算 |
| 申请加入 | PIN、申请信息 | 限流、统一错误、仅建pending，不直接读快照 |
| 批准设备 | ledgerId、requestId | owner批准、邀请单次消费、指定principal |
| 提交快照 | ledgerId、baseRevision、commandId、payload | 权限、体积、幂等、CAS与不可变版本 |
| 撤销成员 | ledgerId、memberId | owner、最后owner约束、后续请求失效 |
| 恢复访问 | 恢复秘密、新principal由会话取得 | 限流、秘密验证、轮换、审计与旧设备策略 |

SQL函数默认尽量使用调用者权限；确需`SECURITY DEFINER`时固定search_path、最小授权、显式身份与成员检查、撤销PUBLIC执行权限。禁止字符串拼接动态SQL接受任意表名或用户自报角色。迁移进入Git，生产密钥不进入Git。

## 08 性能优化方法与候选

### 8.1 先建基线，再定预算

M00已建立Node与独立浏览器基线，详情与原始证据见[M00报告](M00现状与性能基线-2026-11-04.md)。1000行混合关系建账p95约28ms，1万行复杂关系显著超出目标，5万行复杂关系未在测试预算内完成；普通持仓快路径不能代替复杂数据。下面仍是**建议目标**，不表示全部已达成，尤其未测真实用户INP和真机体验。

| 项目 | 建议目标或约束 | 如何测 |
| --- | --- | --- |
| 页面整体体验 | LCP≤2.5s、INP≤200ms、CLS≤0.1 | 生产包；有真实样本时按75百分位分别看移动与桌面 |
| 普通输入/切筛选 | 反馈尽量在100ms内，不因输入重建整本台账 | performance标记、React Profiler、主线程trace |
| 1千行台账 | 建账计算初步目标p95≤100ms | 暖身后重复，包含链/回补/拆档样本 |
| 1万行台账 | 初步目标p95≤500ms；超限先分解瓶颈 | 固定硬件和节流，禁止只跑全普通买单 |
| 长任务 | 日常操作无持续阻塞，单次超过50ms纳入分析 | PerformanceObserver与浏览器trace |
| 包体 | 首屏不加载SheetJS和云同步SDK；新增体积须解释 | 构建清单及真实网络请求 |
| 云同步 | 不阻塞本地保存，传输/解析进度和失败可见 | 网络节流与大包，分段计时 |
| 内存 | 切页/开关弹层重复20次后不持续单调增长 | 固定数据、清理监听后看趋势，非单次绝对值 |

前三项Web Vitals来自公开指导，实验室分数不等于真实用户分位数。[Web Vitals](https://web.dev/articles/vitals)

测试数据层次：62行旧XLSX、项目内CSV fixture；另外构造1千/1万/5万行匿名确定性压力集，并含多股票、先卖后买、两模式、子成交、多代回补、手动链、软删除和异常输入。不要把用户真实文件加入公共fixture。

每条性能证据记录：提交号、构建号、硬件/浏览器、视口、节流、是否首次安装/SW缓存、数据行数与关系数量、预热次数、样本数、median/p95、结果摘要。默认5次预热＋20次测量；高波动时解释原因，不挑最快一次。

### 8.2 领域计算优化

先测`buildLedger`各阶段和真实/沙盒重复成本。候选包括按row/lot/order建立索引，避免热点循环反复`find/filter`；共享同一次派生的Map；将订单、链和汇总的公共计算集中。

每次改算法必须比较完整结构，而非只比较totals。包括排序、稳定身份、来源占用、链分支、奖励FIFO、异常和检查。确保输入不被排序或修改。性能索引只在一次计算或明确修订内有效，不跨账本共享无键缓存。

如果计算仍长，评估Worker，但须加入请求revision、只接受最新结果、取消与错误恢复。Worker延迟结果不能供记成交校验；真实保存仍需读取最新库执行一致的业务规则。不得将并发显示优化变成用旧库存放行成交。

### 8.3 store与React渲染

当前大Context同时带账务、审计、UI会话和操作，值得用Profiler验证广播范围。先分清真实业务修订、审计分页、表单状态与云状态；云上传进度不应重建ledger。

候选顺序：减少不必要整表读取；缓存稳定索引；缩小Context/selector范围；必要时拆只读账务与操作Context。不要为了缓存把依赖漏掉。`useMemo`用于性能，不承担正确性或持久化保证。[React说明](https://react.dev/reference/react/useMemo)

分页审计和成交流水只影响展示，仍须保留历史可检索和完整导出。每次交易不能为了提速跳过已软删除依赖检查。

### 8.4 长列表与大文档

明细、来源列表、回本链和指南长文分别测量。记录少时维持简单DOM，达到实测门槛再引入窗口化；不要预先引入全站虚拟列表。

窗口化要保留：深链定位、浏览器查找替代入口、键盘焦点、屏幕阅读器、展开来源、滚动恢复、选中身份和导出全集。不能用仅渲染行决定应该导出哪些数据。

指南可拆为轻索引＋按文档正文动态加载；离线预缓存、全局搜索、可分享锚点和下载Markdown须继续可用。不要一次请求正文再让搜索结果先显示假“无匹配”。

### 8.5 启动、包体与缓存

- 评估按路由加载Orders/Stats/Manage，处理离线chunk缺失和加载失败重试；保留导航动效与焦点。
- 云SDK在开启云同步或进入相关页时加载，未启用的本地用户不承担认证初始化和连接等待。
- 继续保留SheetJS动态导入、vendor拆包、字体裁剪和估值独立chunk；先验证现有收益，避免重复改写。
- 图片按用途生成合适尺寸；图标原图保留，安装图标、iOS和maskable配置需一起验证。
- SW只缓存公开静态资源。认证、PIN、恢复、云快照API和version检查不得加入公共Cache Storage规则；缓存清理不能触及个人库。
- 不将“删除旧缓存”实现为删除所有同域应用的缓存或强制刷新全部标签。

### 8.6 导入导出与体积

统计读取、解析、映射、校验、预览、写库和重算各段耗时。大文件可在Worker解析，但最终写入计划必须重读当前库，防止预览后库存变化。取消导入不留下半批记录。

JSON、完整Excel和云端恢复共用明确的严格校验契约，同时保留旧格式迁移。不要先恢复再检测坏数据。导出可流式或分块准备，但事务一致性和完整关系优先；失败时不提示文件已成功保存。

## 09 易用性与移动端优化清单

### 9.1 把“当前上下文”放在正确位置

云同步页显示账本名称、设备显示名、远端版本、最后成功时间和dirty状态。日常页面只需克制的同步入口与异常提示，不给每笔成交加网络弹窗。

明确区分：“已保存到本机”“已上传至云端”“已恢复云端第N版”。本地保存成功不能写成“同步完成”；云端检查失败也不能写成“当前最新”。

### 9.2 成交录入

- 股票、方向、实际价、实际量、日期和本次来源在确认区可一眼核对。
- 对参考价、改单价、实际成交价、恢复目标给清楚标签，不默认把计划变成交。
- 一次操作草稿编号稳定，保存中禁重复，超时后提供核对结果而非引导用户新建一笔。
- 错误定位到输入框，保留已输入的有效内容；份额只读、存在依赖等限制解释具体来源。
- 退出草稿或切账本前保护未保存内容。不要偷偷把未保存草稿传云。
- 金额/数量键盘、日期选择、粘贴空格和全角字符在真实手机验证；输入规范化不能改变原意。

### 9.3 状态、筛选与空结果

- 已完成隐藏要有可发现的“查看已完成/全部”入口，显示筛掉的数量，保留固定身份。
- 没有买入推荐时区分：未确认昨收、日内范围无交集、价格不低于最低持仓、没有欠股。
- 区间外不等于成交完成；折叠来源不等于删除来源；云端空账本不等于本地应清空。
- 当前选股、筛选、排序与导出范围一致，跨页返回和分享链接保留可理解的上下文。
- 错误状态给具体下一步，如重新认证、更新应用、下载备份或核对冲突，不只显示“失败”。

### 9.4 手机、键盘与无障碍

320/390/768/桌面视口分别验证；表格独立横向滚动，页面不被撑宽。金额列与操作区不能互相遮挡，触控区初步目标至少44CSS像素，焦点可见，标签与输入关联。

PIN支持整段粘贴、前导0、删除、读屏和数字键盘；不要用9个独立输入框造成焦点陷阱。长数字、记录序号、云端版本允许复制。到期提示不能只靠倒计时变色。

Modal/Drawer继续使用`useScrollHold`；嵌套弹层合并锁定状态。sticky摘要保持inert与焦点隔离，减少动效偏好下仍能完整完成同步与记账。

### 9.5 存储、安装与更新

提供本地存储占用和最近备份信息；可请求持久化存储并显示是否获准，但浏览器可拒绝，不能因此声称数据永不被清理。[StorageManager说明](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)

安装说明区分Safari、安卓浏览器和PWA；系统图标缓存不靠删除数据库解决。更新、重新认证和数据库迁移前保护草稿与本地分支。上传中刷新要能恢复“结果待确认”，不能把未确认状态重置成已同步。

## 11 每轮AI执行协议与可复制提示词

### 11.1 开始前

读取本文“下一轮入口”、AGENTS.md、使用手册、类型图鉴、相关业务文档、最近任务记录与当前git状态；验证当前基线，不假设上轮结果仍适用。识别用户已有改动与无关文件，保留它们。

挑选一个未被阻断的高优任务，写清问题、触发、期望结果、改动边界、验证方法和回退点。对已被明确授权的范围继续推进；需要账号凭证等外部条件时只询问缺少的信息，同时完成不依赖它的工作。不为例行读取、可逆修复和已授权发布反复请求确认。

### 11.2 执行与验收

先取得可重复的失败或基线，再改实现；领域行为变更要有对应反例，低影响文本改动不机械添加镜像测试。性能工作先测再改；一次只验证一个主要假设。

成功时检查“原问题消失、业务不变量保持、相关回归通过、无多余数据修改”。若方案失败，保留发现、撤回无收益代码，不为了展示工作量留下一套无用抽象。

### 11.3 更新本文与交接

## 13 运维、隐私与持续维护

### 13.1 诊断信息

默认诊断只包括appBuildId、协议/结构、错误码、匿名请求ID、阶段耗时、包大小和是否离线。股票名称、数量、金额、备注、原文件名、完整快照、PIN、token和恢复码不进入公共日志、URL或第三方分析。

用户主动导出诊断包时先展示包含范围，提供不含交易内容的版本。测试账号与正式账号分离，错误截图打码。公开仓库只放虚构样本。

### 13.2 配额与清理

定期核对套餐变化、数据库体积、每账本快照数量、匿名身份积累、流量与失败重试。清理过期邀请和未批准请求时不得删除有效成员；删除匿名账号可能级联影响账本，要先验证关联和恢复可用性。

没有定时功能也可通过受控操作触发清理，但不得由任意客户端提交任意保留期限，且不能在每次读账本时执行大规模删除。

### 13.3 变更兼容

先升级读兼容、再启用新写格式；旧客户端不得忽略新字段后回写破坏模式。明确最低兼容版本、停用旧写入的方式和用户升级提示。新schema不是盲目加一：迁移程序、验证fixture、回退策略和云协议都要齐全。

对于当前62行fixture和不同日期的用户CSV，数值分别维护，不把“2100已回补、欠500”与后来“2600已回补、欠0”的两份数据混成一个基准。公开文档的示例只用于解释，不自动向真实库种子数据。
