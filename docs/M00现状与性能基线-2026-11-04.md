# M00现状与性能基线

测量日期：2026-11-04。产品源码基线：`0d0791a`，包含之前的`eba38bc`页面拆包与字体子集化，以及管理页“规划用钱”。本轮只建立基线、保存复现工具和更新交接，**没有修复下列业务反例，没有实施云同步，也没有对产品计算做性能改写**。

这是一次有范围的基线，不是全面无缺陷证明。正式单测、正向浏览器回归与已复现错误可以同时成立。本文中的“复现”代表偏差被观察到，“未复现”仅限列出的输入与调用层级。

## 1 结论与下一步

1. 原有436项单测通过，两个62行fixture的完整Excel往返逐字段一致；真实账务专项通过。
2. C01–C04四个自动链反例仍成立，守恒式全部通过也未检出链归属丢失；不能把链卡正确性简化为总量守恒。
3. **优先阻断项是输入—导出—恢复不闭环**：普通CSV的100.5股可经公共store入口保存，但导出的备份被恢复校验拒绝。不存在的日期也会推进为真实日期。缺必需业务字段的schema 13记录能通过恢复入口。
4. 底层数值函数对Infinity/安全整数仍有风险，但公共手动成交入口已拒绝本轮超大价输入；必须分层表述，不能声称该输入已通过页面保存。
5. 小样本建账不足2ms；1000行混合关系的建账p95约28ms。大量链与来源关系使规模化成本显著上升；普通持仓压力集不能代表完整台账性能。
6. CPU采样优先指向`buildRepairChains`；后续P01应围绕链内遍历与索引建立假设。不要先增量化整个store，也不要为几十行数据引入Worker。
7. 下一轮先做**B02.1“普通导入股数闭环”**：非法股数在预览/提交边界拒绝，合法导入必须可再次导出恢复。随后进入M01快照契约，补齐必需字段与ID严格校验。云同步仍未实现。

### 6.3 大规模复杂场景与超时

60秒是单个进程**整组测量预算**，包含启动、构造、预热和正式样本。10000行mixed首次建账4896.78ms，首次snapshotViews为6353.69ms，两组均未在60秒预算内完成全部25次；不能把这两个单次值写成p95。

50000行mixed在60秒预算内未报告首个完整结果，已终止测试进程；没有median/p95和完整输出等价结论。这里证明当前测试成本过高，不等于精确测得“单次建账超过60秒”。

10000行mixed放宽到180秒的独立补测已完成，5次预热＋20次采样，中位5935.63ms、p95为7388.93ms；输入前后未变，首尾完整输出hash相同。初次8420.40ms不纳入正式分位数。原60秒超时记录保留，两次运行并不混合统计，测量波动与硬件条件仍需在后续比较中控制。

### 6.4 CPU热点

独立Node CPU profile覆盖Vite Node加载和25次1000行mixed建账，总采样约1804ms。`buildLedger`含子调用采样548.82ms，其中`buildRepairChains`335.76ms，约占建账栈内采样的61.2%。其次可见价位槽收集及逐股汇总。

这是采样归因，不是精确阶段计时；inclusive父子时间不能相加。Vite转译后的行号不作为源码固定定位，按函数名和当前源码追踪。原始profile保留，后续P01可用同脚本与相同输入hash对照。

建议P01先测链分支中按股票/row/lot/exec重复筛选的成本，再决定索引；不能为提速改变历史顺序、FIFO、归属或输入数组。
